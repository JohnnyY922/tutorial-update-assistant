# Trace · 教程变更定位助手

**产品功能更新后，快速找出哪些教程需要同步修改，并生成可核对的修改清单。**

面向产品运营、知识库维护者和技术写作者：导入一个包含多篇教程的 Word 文档，描述本次变更，即可查看受影响的原文、所在位置、修改原因和建议内容，最后导出 CSV 交给维护人员处理。

**例如：平台功能从「Agent」更名为「Skills」时，哪些教程要改？哪些 AI Agent 概念、链接和代码参数应该保留？** 这是项目内置示例展示的场景。

> 项目状态：可交互的前端原型。当前使用本地规则分析；已预留 AI 上下文分析接口，尚未连接真实模型或部署后端。

## 一眼看懂使用流程

```mermaid
flowchart LR
    A[① 导入 Word 教程合集] --> B[② 描述本次产品变更]
    B --> C[③ 核对结果并导出清单]
```

| 步骤 | 用户做什么 | 页面提供什么 |
| --- | --- | --- |
| ① 导入教程 | 上传 `.docx`，核对教程目录 | 解析标题、段落、列表和普通表格；支持调整教程拆分 |
| ② 描述变更 | 填写变更说明、新旧内容，按需设置例外 | 明确本次需要检查的内容与保留条件 |
| ③ 核对与导出 | 筛选结果，查看原文上下文，导出 CSV | 提供“建议修改 / 待确认 / 无需修改”三类候选结果 |

**结果示例**（以 Agent → Skills 更名场景说明）：

| 原文内容 | 判断 | 处理方式 |
| --- | --- | --- |
| 进入 Agent 功能页面，点击「创建 Agent」按钮 | 建议修改 | 将功能名称替换为 Skills，保留其余描述 |
| AI Agent 是一类能够自主规划并执行任务的智能体 | 无需修改 | 保留通用技术概念 |
| 在 Agent 菜单中点击「新建」，也可以使用 `/agent/create` 路径直接进入 | 待确认 | 同段涉及显示名称与技术路径，需要分别核对 |

每条结果都可以展开查看**原文位置、判断原因、建议内容与上下文**。导出的是修改清单，原 Word 文档保持不变。

## 快速体验

启动项目后，在首页点击 **「用示例体验一次」**，无需准备文档即可走完主要流程。内置示例包含 6 篇教程，展示名称变更、概念保留、代码保护和待确认等情况。

在项目目录运行：

```bash
python3 preview.py
```

浏览器访问 **http://127.0.0.1:5173**。macOS 也可以双击 `启动预览.command`。端口被占用时，可运行 `python3 preview.py --port 5174`。

项目使用浏览器 ES 模块，需要通过 HTTP 访问，不能直接双击 `index.html`。Tailwind 样式和 JSZip 已随项目打包，日常预览无需安装 npm 依赖。

## 这个项目解决什么问题

产品名称、入口或操作流程发生变化时，维护者需要逐篇检查旧教程。简单的关键词替换难以区分功能名称、通用概念和技术标识，也无法直接形成便于执行的修改清单。

Trace 将这项工作整理成“定位 → 判断 → 核对 → 导出”的流程：候选内容关联原文位置；信息不足的内容进入待确认；维护者可以带着上下文判断是否修改，再将结果交给后续执行人员。

## 产品与交互设计

- **分步完成任务**：首页聚焦导入，变更配置与结果核对放在独立页面，降低首次使用的信息负担。
- **按需展开细节**：目录调整、范围与例外、任务记录放在二级窗口；结果详情使用抽屉，支持上一条 / 下一条。
- **让判断可核对**：结果展示原文、位置、原因和建议，支持查看上下文，并按教程、状态和关键词组合筛选。
- **覆盖异常与回退**：提供文件校验、空结果、部分失败和重试状态；修改配置后标记旧结果，保留原任务快照。
- **适配不同屏幕**：支持桌面与移动端布局，采用更大的正文和留白，移动端详情以全屏方式展示。

| AI 接口准备 | 统一异步调用、完整教程上下文传递、响应校验、超时处理与分析来源标记 |

## 技术实现

采用 **HTML + Tailwind CSS 3.4 + 原生 JavaScript（ES Modules）**。使用 JSZip 解包 Word 文件并解析其中的 XML；默认模式下，文档解析和规则分析均在浏览器内完成，文档内容不会上传。

页面交互、文档解析和分析服务分开组织，方便后续替换分析能力并沿用现有页面与导出流程。

```text
index.html / styles.css       页面结构、组件样式与响应式布局
app.js                       页面状态、交互、任务快照与导出
parser.js                    DOCX 解析与文本块生成
engine.mjs                   本地规则、教程分组与 CSV 生成
analysis-config.js           分析模式与服务地址配置
services/                    统一分析接口、请求与响应校验
server/                      后端处理模板与模型提示模板
tests/                       接口与数据校验测试
API_CONTRACT.md              AI 接入步骤及数据协议
preview.py                   本地预览服务
```

### AI 上下文分析如何扩展

当前配置为 `local`。未来切换为 `api` 后，前端会将**单篇教程的全部文字块、标题、段落顺序、文档目录和变更条件**发送到自己的后端，再由后端调用模型。请求不会只保留关键词命中的段落。

已实现的接口校验会检查请求编号、教程编号和段落覆盖情况，拒绝未知段落或不匹配的原文引用；服务失败会明确提示，不会悄悄切换为本地规则。协议校验保证返回数据符合约定，真实模型的漏检、误报和建议质量仍需单独评估。

实际接入还需要部署后端、实现身份校验和模型调用，并将密钥保存在后端环境变量中。GitHub Pages 可承载前端，后端需单独部署。详见 [AI 接口约定](API_CONTRACT.md)。

## 当前边界与后续方向

- 当前是规则分析原型，尚不具备真正的 AI 上下文理解能力；复杂范围与例外条件仍需人工核对。
- 图片、截图、文本框和批注不参与分析；复杂嵌套表格及非标准 Word 结构仍需兼容性验证。
- 支持的输入上限为 20 MB、10,000 个文字段落、200 万字；超限会提示拆分，不会静默截断。
- 文档与任务仅保存在当前页面内存中，刷新后清空；目录调整不改写原 Word。
- 尚无账号、云存储、内部知识库连接或自动发布能力。

后续重点是接入真实模型，使用人工标注样本评估结果质量，并完善长教程的上下文分块与服务端访问控制。
